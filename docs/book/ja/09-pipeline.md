# ドキュメントパイプライン


## 最初の利用者の道筋

チームがファイルをアップロードし、ワークフローがそれを処理する。テキストを抽出し、JSON スキーマに照らして構造化されたフィールドを取り出し、書式のテンプレートを埋め、結果を翻訳する。四つの中核ツールが組み合わさって、同梱の `process-upload` ワークフローになる。スキーマ、テンプレート、ロケールは入力なので、一つのワークフローが新しいコードなしに請求書と申込書の両方に仕える。すべての出力は元のドキュメントのそばに置かれる保管庫のドキュメントであり、元の付与と来歴の行を伴う。

## 印をつけるのではなく拒否する

フィールド抽出器はモデルの返答をスキーマに照らして検証し、必須フィールドの欠落、数値を求めた場所の文字列、そして発明された鍵を拒否する — `additionalProperties` を持たないオブジェクトのスキーマは*閉じている*。これは JSON Schema の既定からの意図的な逸脱である。テンプレートの描画器は、データが満たせないプレースホルダを空欄として描くのではなく拒否する。合計欄が空のまま完成したように見える書式こそ、この設計全体が防ぐために存在する失敗である。ステップは一度だけ再試行する。スキーマの不一致はモデルの間違いであり、温度ゼロで二度目に読ませれば多くの場合は適合する。

## テンプレート

Markdown と HTML のテンプレートは `{{field}}`、ドット区切りの経路、そして `{{#each items}}` のブロックを使う。DOCX のテンプレートは zip であり、その `word/document.xml` が同じプレースホルダを運ぶ。これが聞こえるより難しい理由が二つある。Word は、著者が手を止めた瞬間や綴り検査が覗いた瞬間に、プレースホルダを複数の run に分割してしまう。だから `{{` とその `}}` のあいだにあるタグはすべて、描画の前に取り除かれる。そしてもう一つ、明細は項目ごとに表の一行を欲しがるので、本文が `{{#each items}}` だけの行がブロックを開き、`{{/each}}` だけの行がそれを閉じる。PDF の描画は見送っている。PDF の描画器はどれも依存物であり、そもそも人が編集するのは DOCX か HTML の書式である。

## トリガ

トリガとはチーム単位の購読である。この接頭辞とこれらの内容型に合致するドキュメントが届いたら、それを渡してあのワークフローを走らせる、というものである。トリガが評価される場所はちょうど一つ — `repo-put!` の末尾にあるフック、バージョンが確定した後である — ので、コンソールからのアップロード、テキストドキュメントの互換層、S3 の `PUT` が構造上すべて覆われる。合致すると、*アップロードした人*として、そのスコープもすべて含めて実行が投入される。実行が読めるのはアップロードした人が読めたものだけであり、その出力は実在する誰かが所有する。発火はバージョンごとにちょうど一度である。パイプライン自身の出力が、それを生んだトリガを再発火させることは決してなく、参加を表明したトリガが、自分が始めた実行の出力で発火することも決してない。この規則がないと、参加を表明したトリガはテストの中で、流出制限が止めるまでに自分自身を五十回走らせた。既定の `files:*` スコープで発行された S3 キーはワークフローを開始できない — トリガの履歴がそうはっきり言う — 発火させたい接頭辞には `workflows:run` が必要である。
