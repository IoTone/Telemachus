# ジョブの待ち行列


## ジョブとは何か

ジョブとは一つの行である。チーム、ユーザー、種別、JSON のペイロード、優先度、状態。実行中のジョブについてメモリに置かれるものは何もない。だから再起動で仕事が失われることはなく、だからワークフローのステップ、一括翻訳、別のマシンへ回されたモデル呼び出しが、すべて同じものでありうる。上限のあるワーカースレッドのプールが待ち行列を汲み出す。各スレッドは一つのジョブを確保し、その種別のハンドラを走らせ、結果をその行に書き戻す。

二つの方針は、ハンドラの内側ではなく確保の時点で適用される。だからどの種別もそれを忘れることができない。一つは**チームごとの同時実行上限**で、あるチームの一括処理がプールを独占するのを止める。もう一つは**クォータの受け入れ判定**で、予算を超えたチームのジョブを失敗させるのではなく待ち行列に留める。何も実行されていないのに動きの止まった待ち行列は、たいていは AI 予算を使い切ったチームであり、それはプラットフォームが正しく働いている姿である。

## 一つを確保する

確保は些細に見えるが、そうではない。プールは待ち行列の行を走査し、候補を一つ選び、実行中へ切り替える — しかしその切り替えは、その行がまだ待ち行列にあることを*条件とする*必要があり、そして条件は誰かが結果を読まなければ無価値である。

    UPDATE jobs SET status='running', started_at=CURRENT_TIMESTAMP,
                    lease_until=?, executor_id=?, claim_token=?
     WHERE id = ? AND status='queued'
     RETURNING id

確保は、行が返ってきたときにだけ信じられる。これは見かけより重要である。ドライバは PostgreSQL では影響した行数を報告するが SQLite では報告しないので、行数は方言に依存する答えになってしまう。一方 `RETURNING` はどちらでも動く。更新が何にも合致しなかった確保者は、別のワーカーが握っているジョブを走らせるのではなく、次の候補へ移る。これより前は、排他は一つのプロセスの中のロックに頼っていた — プロセスが二つになるまでは問題なかった。

## ワーカーが死ぬとき

すべての確保は**リース**を伴う。保持者が仕事をしているあいだ更新し続けるタイムスタンプである。保持者が死ねばリースは失効し、回収役がそのジョブを試行回数を一つ増やして待ち行列へ戻す。三回を過ぎれば本当に失敗させる。これはインプロセスのプールにも、遠隔のワーカーとまったく同じように当てはまる。そうでなかったころは、プロセスが死んだプールのジョブが永久に `running` のまま座り、そのチームの同時実行枠を食い続けていた。古いビルドが残したジョブ — 実行中で、リースのないもの — は、プールの起動時に待ち行列へ掃き戻される。

回復はより微妙な問題を生む。そしてそれが覚えておく価値のあるものである。元の実行がまだ生きているうちにリースが失効したとしよう。回収役がジョブを待ち行列に戻す。*同じ*保持者がもう一度それを確保する。最初の実行がついに終わり、結果を書く。状態は一致する。保持者も一致する。どちらの検査も、二つの試行を見分けられない。そこで、確保はそのたびに**隔離トークン**を鋳造し、その試行についての後続のすべての書き込みがそれを運ぶ — 最終的な書き込み、リースの更新、そして遠隔ワーカーの心拍、完了、失敗である。待ち行列への差し戻しはその列を消し、最終的な書き込みもすべて消す。前の試行のトークンが再び一致することは決してなく、現在の試行からの二度目の書き込みも一致しない。

    claim  -> id + lease_until + claim_token
    heartbeat / complete / fail  -> その claim_token を運ばなければ 409

## 仕事の側へやって来る実行基盤

推論ホストが、サーバから呼び出せる場所にいる必要はない。**pull 型の実行基盤**は、自分が走らせられるジョブを長いポーリングで待ち、走らせているあいだ心拍を送り、結果を投稿するループを回す — だから NAT の後ろや tailnet の上からでも、外向きの接続だけで働ける。その資格情報は、スコープが `jobs:execute` だけの API トークンであり、一度だけ表示され、実行基盤の行に結び付けられる。実行基盤はそのトークンを通して解決され、リクエストの中のフィールドを通して解決されることは決してない。

**遠隔の種別**は、インプロセスのハンドラなしで登録される。プールはそれを飛ばし、ワーカーだけがそれを確保でき、その結果はその種別が供給しなければならない関数によって検証される。代わりに厳しくしてくれるローカルのハンドラが存在しないからである。同梱されているのは `infer.chat` — まさに `run-chat` が話す通信路である — なので、同期的なモデル呼び出しは子ジョブになってワーカーを待ち、モデルを使うすべてのツールは、そのチャットが別の場所へ回されても変わらずに動く。子ジョブは親を運び、確保の時点でチームの上限から除外される。そうでなければ、上限が二の環境で二つの親が、誰も確保できない子ジョブをそれぞれ永久に待つことになる。

## どのモデルが何を走らせるか

*モデルの役割*は実行基盤の名前へ解決される。まずチームの設定、次に環境変数、最後にローカルのモデルである。同梱されている役割は一つ — `utility` — で、これが量のある仕事を担う。知識グラフの抽出、パイプラインのフィールド抽出と翻訳、そして翻訳マネージャの下書きである。人のチャットがそこへ行くことは決してない。ツールは自分のモデル呼び出しの周りでこの役割を設定するので、GPU の箱は、どのツールもその存在を知らないままに一括処理を引き受けられる。存在しない実行基盤を役割に設定することは拒否される。そうでなければ、打ち間違いがすべての抽出を静かにローカルのモデルへ送り返してしまう。
