# ドキュメント保管庫


## オブジェクト、バージョン、ブロブ

保管庫のオブジェクトは所有できるリソースであり、ノートが持つのと同じ三つのフィールド — チーム、所有者、公開範囲 — を持つ。だから新しい認可コードなしに `can?` がそれを統べる。同じキーに二度書き込むと、一方を置き換えるのではなくバージョンが追加される。付与や URL が指すのは、安定した存在であるオブジェクト ID である。バイト列は SHA-256 を鍵とする内容アドレス方式のストアに置かれ、*組織*ごとに名前空間が分かれている。テナントをまたぐ全体的な重複排除は、存在を漏らす神託になってしまう。ストアにプリンシパルが渡されることは決してない — 名前空間とダイジェストだけである — ので、ストレージのバックエンドには間違えるべき認可が存在しない。

アップロードは生の `PUT` の本体であり、JSON の中の base64 では決してない。ダウンロードはすべて添付ファイルとして、`nosniff` と拒否する CSP を付けて配信される。短いインライン許可一覧に載っている型だけが例外である。SVG と HTML が決してインラインにならないのは、それらがコンソールとオリジンを共有するからである。

## S3 エンドポイント

二つ目のリスナーが、`aws`、`rclone`、`boto3`、Cyberduck が動くだけの S3 を話す。SigV4 は仕様から実装され、AWS の公表するベクタに固定されている。バケットはパス形式で、チームのスラグが名前になる。範囲指定の GET（必須である — CLI は大きなオブジェクトを並行した範囲指定で取得する）、マルチパートアップロードにも対応する。アクセスキーはスコープを持つ通常の資格情報であり、秘密鍵は平文で保存される。SigV4 が検証のためにそれを必要とするからである。実装していないサブリソースは 501 を返し、黙って成功を装うことは決してない。署名付きリンクは呼び出し元自身の最新のキーで署名されるので、そのキーを失効させればリンクも死ぬ。

## 共有と来歴

共有は前章の権限モデルそのものであり、すでに存在していた付与のテーブルの上に乗っている。来歴は `repo_derivations` である。ワークフローがあるドキュメント*から*別のドキュメントを書くとき、出力は作成の瞬間における元の公開範囲と有効な付与を受け継ぐ — 元が非公開なら最初のバイトから非公開である — そして派生の行が、元のバージョン、実行、ステップを名指す。それ以降、二つのドキュメントは互いに独立である。「この書式はどこから来たのか」はクリック一つで分かる。
