# 認可のモデル


## 権限とロール

権限とは `resource:action` という形の文字列である。ロールはそれらに名前を付けた集合であり、組み込みのチームロールは owner、admin、member、viewer の四つ、その上に二つの組織ロールが乗る。ワイルドカード（`files:*`、`*:read`、`*:*`）もあるが、チームロールが何を付与しようと到達できない層が二つある。`instance:*` は運用者だけのものであり、`org:*` は会社の組織ロールだけのものである。すべての権限は宣言のそばに一行の説明を持つ。説明のない権限を付与する組み込みロールは、読み込み時に失敗する。生成される `permissions.md` がカタログとロールの対応表を示す。

## `can?` の順序

1.  **組織のゲート。** リソースが別の組織のものであれば、無条件に拒否する。他の何かを参照する前である。これがマルチテナンシーを健全にしている。共有も、付与も、スコープも会社の境界を越えて潜り込むことはできない。それらを尊重するはずの検査が、そもそも走らないからである。

2.  **層。** `instance:` の権限は運用者フラグを必要とし、`org:` の権限は組織ロールを必要とする。

3.  **ロール、あるいは付与。** プリンシパルのチームロールがその権限を含んでいなければならない — *あるいは*、そのリソースについてその権限を名指すリソース付与を持っていなければならない。付与とは委譲である。編集可能なドキュメントを viewer に共有すれば、その viewer はそのドキュメント一つを編集できる。member に `manage` の権限を渡せば、その人はさらに先へ共有できる。共有の実装より前は、付与は到達可能性を広げるだけで、ロールに欠けている権限を与えることはできなかった。それでは「編集のために共有する」が嘘になっていた。

4.  **所有者は可。** リソースの所有者は、そのリソースについてチーム層のすべての権限を持つ。同僚のドキュメントを削除できない member も、自分のものは削除できる。

5.  **スコープ。** API トークンや S3 キーは、その発行者に上限をかける。スコープの一覧もまたその権限を含んでいなければならない。スコープは狭めるだけで、広げることは決してない。

6.  **到達可能性。** 非公開のリソースに到達できるのは、その所有者、運用者、そして付与を受けた者である。チームに公開されたものにはそのチームの誰でも到達でき、共有されたものには所有者と付与を受けた者が到達できる。

## 権限のまとまり

ドキュメントを共有する人は、権限の文字列を選ぶわけではない。閲覧・編集・管理のいずれかを選び、プラットフォームがそれに対応する付与の行を書く。閲覧は `files:read`、編集はそれに `files:write` を加えたもの、管理はさらに `files:delete` と `files:manage` を加えたものである。ワイルドカードは決して使わない。付与の行は、書かれているとおりのことだけを意味する。さらに先へ共有できるのは管理だけである。付与は同じ組織のユーザーまたはチームを名指すことができ、有効期限（エポック秒。`BIGINT` である。32 ビットの列が PostgreSQL のスモークで 2099 年の期限に桁あふれした）を持つこともできる。期限切れの行は無視されるが、削除はされない。誰に何が与えられたかの監査記録そのものだからである。

## マルチテナンシー

既定では無効である。フラグを立てると、チームの上に*組織*が乗り、スーパー管理者がインスタンスを運営し、組織管理者が一つの会社を運営する。組織管理者は管理はするが読まない。`documents:read` もなく、`chat:use` もない。チームのデータを必要とする会社の管理者は、そのチームに member として参加し、その参加は監査される。手順 0 のゲートは機能フラグを読まないので、データの入ったインスタンスでフラグを下ろしても、管理用の面が隠れるだけで強制は続く。
