# ツールとエージェント


## ツールを宣言する

    (define-tool doc_text
      #:description "Return the text of a repository document."
      (object string #:description "The repository object id")
      (version string #:optional #:description "A specific version id"))

    (register-tool! "doc_text" doc_text "files:read"
                    (lambda (conn principal args) ...))

`define-tool` は、モデルが見る OpenAI 互換の関数スキーマへ展開される。だから宣言と契約は一つのものである。ハンドラはデータベース接続、呼び出し元のプリンシパル、そして解析済みの引数を受け取る。自分の権限を自分で検査し、自分の AI 消費を自分で計量する。文字列でない結果は、エージェントの境界で JSON に符号化され、ワークフローの中では値のまま保たれる — リストを返すツールは `map` ステップにそのまま流れ込む。

## レジストリ

組み込みツール、プラグインのツール、ワークフローのツールは、すべて一つのレジストリに収まり、出自の印が付く。チームはどのツールも無効にできる。エージェントは有効なツールだけをモデルに提示し、ディスパッチは無効なものを拒否する。プラグインはプラットフォームの権限でインプロセスに動く — `plugins/` に置くことがその同意である — そしてサンドボックス化されたプロセス外のプラグインは、別の、権限を限定した仕組みとして存在し、標準入出力の上で改行区切りの JSON を話す。

プロセス外のツールは、テキストだけでなく*構造*で答えることもできる。その結果メッセージは、人間向けのものと並んで任意の構造化フィールドを運ぶ。それがないと、そうした答えはワークフローが束縛する時点でみな JSON の*文字列*になってしまい、後続のステップには、プラットフォームがいま文字列化したものを解析するためだけに存在するインプロセスの橋渡しが必要になった — 一方でインプロセスのツールは、何スライスも前から値を返す自由を持っていた。プラットフォームは、文字列が本当は JSON のつもりだったのだと推測することは決してしない。プラグインが構造化フィールドを送ることで、そう言うのである。

## モデルとの継ぎ目

モデルを呼ぶものはすべて `domain/ai/executor.rkt` の `run-chat` を通る。そして構造化出力を必要とするツールは、モデルをパラメータとして受け取る（`current-doc-chat`）。ユニットテストはそれに台本を与える。HTTP のスモークは `test/mock-llm.rkt` を使う。これは決定的な OpenAI 互換のサーバで、チャットモードでは `needle: reply` の対を集めたファイルから答え、最も長い needle が勝つ。モデルの URL が設定されていれば、同じスモークが本物のモデルに対して走る。こうして、モデルを必要とするパイプラインが CI では数秒で試験され、開発者のマシンでは qwen2.5:7b に対して検証される。

## メッセージが運べるもの

メッセージの内容は文字列*または*パーツのリストである。後者はゲートウェイやマルチモーダルのサーバが送ってくる、OpenAI 互換の `[{type: "text", text: ...}]` という形である。これをすべての経路 — エージェントループ、チャットのエンドポイント、ストリーム、そして pull の通信路 — のために一つのモジュールが決めているので、それらが食い違うことはありえない。テキストのパーツは連結される。パーツを運んでいて、しかもテキストが*ない*内容は、静かな空文字列ではなく、名前の付いたエラーになる。その区別こそがすべてである。空の返答を作り出してはならない。何も言わなかったモデルと区別がつかなくなるからである。内容が存在しない、あるいは空であることは、依然として正当に「空」である — ツール呼び出しだけのターンがまさにそう見える — ので、エージェントの解析器が例外を上げるのは、そのターンにツール呼び出しも無いときだけである。これは一年にわたって静かなバグだった。`(if (string? c) c "")` がすべての返答を読んでいたので、パーツで答えたプロバイダは空のメッセージを生み、誰も文句を言わなかった。

呼び出し側は形を要求することもできる。`response_format` — `text`、`json_object`、`json_schema` — はプロバイダへ送られ、*かつ*返答がここで検査される。ほとんどのローカルサーバはこのフィールドを完全に無視するので、そうしなければスキーマの要求に対して散文が返ってきて、呼び出し側はそれを適合したものとして解析してしまう。検証に使うのは、ドキュメントパイプラインの抽出と同じ部分集合の検証器であり、同じ `$.total: expected number, got string` という拒否である。モデルのない模擬の代替は、大文字化した反響を適合した JSON と偽るのではなく、形の要求を拒否する。ストリーミングはストリームが終わった時点で形を判定し、最後のイベントでその判定を報告する。答えがすでに出て行った後で例外を上げるほうが、より悪い。
