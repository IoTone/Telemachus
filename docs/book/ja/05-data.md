# データとマイグレーション


マイグレーションは `domain/db/migrations.rkt` にあり、起動時に適用される一つのリストである。どの文も方言に依存してはならない。いまは SQLite、二つ目の対象は PostgreSQL であり、ユニットスイートと二つのスモークスイートはあらかじめ設定された `DATABASE_URL` を尊重するので、すべてがどちらに対しても走る。何かを完了と呼ぶ前に PostgreSQL で確かめること。この本の著者たちはそうしており、それによって int4 の桁あふれ、プレースホルダの書き換え漏れ、そしてすべての S3 一覧表示を壊していたタイムスタンプ形式を捕まえた。

その実行から得られた規則のいくつか。

- 予約語は引用符で囲む（`"window"`）。

- 期間はタイムスタンプの演算ではなく、エポックの整数列で表す。`CURRENT_TIMESTAMP` は秒の解像度しかなく、その文字列表現は方言によって異なる。一秒の中で「新しい順」に並べなければならないものは、自分専用のエポック列を持つ。監査ログはこれを遅くに学んだ。文字列のタイムスタンプで並べ、次にランダムな UUID で並べていたので、同じ秒に書かれた二つのエントリは、実際に起きたこととは無関係な順序で返ってきた — レビューの判断が、それを引き起こした評価より前に読まれることもありえた。ここで*足りなかった*ものにも注意してほしい。ミリ秒である。書き込みの集中は単位が何であれ一つの刻みの中に収まるので、列はマイクロ秒であり、*かつ*書き手がプロセス内で厳密に増加するよう値を押し上げる。時計の読み取りは並び順の鍵ではない。

- upsert には `ON CONFLICT ... DO NOTHING` または `DO UPDATE` を使う。どちらの方言も、衝突対象を名指す構文を解する。

- `hasheq` の反復順序は Racket のプロセスをまたいで安定しない。再現可能でなければならないもの — ディスクに書く JSON、生成される表の列の順序 — に、それを決して頼らないこと。

ユニットテストの土台は `test/db-fixture.rkt` にある。`(fresh-db)` は、マイグレーション済みで他から隔離されたデータベースを返す。SQLite ではメモリ上に、PostgreSQL では土台ごとに専用のスキーマとして作られる。テストファイルは並行して走るからである。

## 開いてみるファイル

`domain/db/migrations.rkt`、`test/db-fixture.rkt`。
