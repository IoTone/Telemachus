# TMach を拡張する


## 四つの継ぎ目と、一つの接頭辞

プラグインはマニフェストと入口モジュールを持つディレクトリであり、起動時に読み込まれる。それは四つの継ぎ目を埋めることができ、拡張の契約はその四つで尽きている。

- **ツール** — `(provide tools)`。モデルが呼べる能力である。組み込みと同じレジストリを通して登録されるので、ツールごとの権限とチームごとの有効化が、プラグインが何もしなくても適用される。

- **ワークフロー** — `(provide workflows)`、またはディレクトリに置いた仕様ファイル。API から公開された仕様とまったく同じように検証され、最初に参照された時点でチームへ実体化される。プラグインは読み込みの時点でチームを持たないからである。

- **HTTP ルート** — `(provide routes)`。`/api/x/<plugin-id>/...` に載る。接頭辞はプラットフォームが固定しているので、プラグインが中核のルートや他のプラグインのルートを覆い隠すことはできない。すべてのルートはベアラトークンを要求し、それが名指す権限はハンドラが走る前に検査される。そして形の崩れたエントリは、一時間後のリクエストではなく*そのプラグインの読み込み*を失敗させる。

- **ジョブ種別** — `init!` から登録し、`x.<plugin-id>.<name>` と名付ける。プラグインの種別は普通のジョブである。投入したチームとユーザー、同時実行の上限、クォータの受け入れ判定、組織のゲート、キャンセル、リースのすべてが適用され、そのどれもプラグインから受け継がれない。遠隔の種別は検証関数を供給しなければならない。代わりに厳しくしてくれるインプロセスのハンドラが存在しないからである。

## プラグインはどこで見つかるのか、そして見つからないとどうなるのか

組み込みのディレクトリは常に探される。`TMACH_PLUGINS` は `:` 区切りの一覧としてそこへ足す。そして文字どおりの `-` というエントリは、自分のものだけを出荷するつもりの配備のために組み込みを外す。これはかつて読み込む*唯一の*ディレクトリを名指していたので、自分のプラグインを足すとドキュメントパイプラインと他の同梱プラグインすべてが静かに消えた — ワークフローが失われたまま健全そうに立ち上がるインスタンスである。

その形 — 健全に見えて静かに欠けている — には名前を付ける価値がある。ローダはそれを二つ目も抱えていたからである。読み込み中に例外を上げたプラグインは捕まえられ、記録され、飛ばされる。それは正しい。一つの悪いプラグインがサーバを止めてはならない。しかしそれは*記録されるだけ*で、六十行の中の一行だった。そしてインスタンスはその後、そのプラグインのツール、ワークフロー、ルート、ジョブ種別がただ無い API を提供した。いまは失敗が保たれる。プラグインの一覧の隣に `failed` の一覧があり、起動時に幾つなぜ失敗したのかを言う警告の塊があり、そもそも起動を拒否する厳格モードがある。二つのプラグインが一つの ID を主張することも、静かな覆い隠しではなく失敗である。

関連する罠を一つ。まさにこれを生んだからである。`raco make` はプラグインの入口モジュールに届かない。ローダがそれを `dynamic-require` するからである。したがって Racket の更新は `plugins/<id>/compiled/` の下に読み込めない古いバイトコードを残す — そして上記の変更より前は、それを誰も読まない一行で言っていた。

## 自分の画面

プラグインは自分のページを二つのディレクトリから配信し、その違いは誰が読んでよいかである。`landing/` は `/beta/bundle/<id>/` で公開され、公開キャッシュに載る — 見込み客にリンクを送るマーケティングの導線である。`bundle/` は `/api/x/<id>/bundle/` で認証を要し、ベアラトークンを要求し、`private, no-store` で応答される。顧客向けの画面は後者に属する。それが存在する前は前者だけがあり、サインイン済みの画面をそこから配信すれば、顧客のページを公開キャッシュの後ろに置くことになっていた。

資産はバンドルの中に入れて出荷する。コンソールの方針は同一オリジンなので、CDN のフォントやスクリプトは遮断される — 意図してそうしてある。

その認証付きディレクトリについて、その上に何かを建てる前に知る価値のあることが二つある。そこのファイルは、チェックアウト配下の固定された経路ではなく、*ローダ*がそのプラグインを見つけた場所から配信される。別の場所から読み込まれたプラグインは、かつてツールとルートを完璧に配信しながら、持っているページはすべて 404 を返した。そしてそこのページは、ブラウザで単に開くことができない。トークンはコンソールの保管庫に住んでおり、ページ遷移はベアラを運ばないからである — スモークが一年通り続けたのは、`curl` がブラウザの決して送らないヘッダを送るからである。開くには、手元にあるトークンで短命な**チケット**を鋳造する。最初の応答がそれを、そのプラグインのバンドル経路に限ったクッキーとして設定するので、ページ自身のスクリプトとスタイルシートは、すべての URL に引きずられることなく後に続く。サインイン時に発行されるセッションクッキーではない。JSON の API はクッキーなし・CSRF の面なしという性質を保ち、こちらは一つのプラグインの静的ファイル以外のどこにも届かない。

## 顧客の色をまとう

ブランディングの文書は*テーマ*を運ぶ。背景、表面、文字、控えめな文字、ブランド、ブランドの上に乗る文字、角の丸み、モード、そしてフォントである。これはオンボーディングの導線がすでに使っていたのと同じトークンの語彙なので、配色は一度書けば両方がまとう。そして組織ごとの扱いが無料で付いてくる。会社のブランディングは同じ鍵の下のもう一つの文書だからである — 自分のホスト名を持つ会社は、誰かがサインインする前からテーマをまとう。

二つの規則がこれを正直に保つ。未知のトークンは無視ではなく拒否される。静かに何もしないトークンは、組み込み側がテーマ機能が壊れていると結論する道だからである。そしてコントラストはサーバによって*強制*され、単に警告されるのではない。本文、控えめな文字、パネル上の文字、ボタンのラベルには WCAG AA、ブランドとその地には低めの基準である。これは人がサインインする画面であり、自分のサインインのリンクを見えない色にしたインスタンスには、UI を通って戻る道がない。ボタンの地はトークンではなくコンソールが混ぜる色なので、検査されるのはその混色である — ブランドそのものを検査すれば、完璧に描かれるテーマを落とし、そうでないものを通してしまう — そして配色のどちら側が暗い側なのかは、モードのトークンから読むのではなく測って決める。

## 使えないもの

はっきり述べておく。誰も望みの上に設計しないために。プラグインは中核のコンソールにタブを足すことができない — 代わりに自分の画面を配信する。機能フラグはチームごとであり、インスタンス全体の切り替えはないので、「この配備にはチャットが無い」はすべてのチームについてそうすることを意味する。そしてホットリロードはないので、プラグインを足すには再起動が必要である。
