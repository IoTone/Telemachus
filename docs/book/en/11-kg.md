# The knowledge graph, and retrieval


Entities and the relations between them, extracted from the team’s documents, every fact traceable to the document and version that asserted it. Nothing enters the graph without a source, and that one rule makes the rest fall out.

**Visibility is inherited, never assigned.** A fact is visible to a principal if at least one of its mentions is on a document they can read; mentions are filtered per row, so a private memo’s snippet stays private even when the team can see the fact through a report. An entity a caller can see no mention of does not exist for them, and the API does not distinguish that from a missing id.

**Validation is the provenance.** The extractor asks the model for a strict shape and refuses a snippet that is not a verbatim substring of the text, a relation to an entity not in the same reply, or a nameless entity. A new version of a document supersedes its old mentions; deleting a document forgets its facts; an entity or relation with no mention left is pruned.

**Deliberately narrow.** Deduplication is by type and normalized name; cross-type merging is where knowledge graphs go to die. There is no graph query language — two hops from a named entity covers the questions people have — and no visualization library: the tab is lists with citations, and the agent’s `kg_query` tool answers in text with the documents that said so.

## Retrieval

The graph answers “what do we know about Acme”. The other half of the question —
“what did we read about this” — wants passages, and that is a separate stack built
in six steps, each landing with its own tests before anything called it.

**The chunker counts characters, not tokens, because there is no tokenizer on this
side.** A token count computed here is a guess wearing a measurement’s clothes, so
the unit is 1,024 characters with 15% overlap, which is the design’s 256 tokens at
roughly four English characters to the token. The offsets are the extractor’s own
coordinates — the same ones a page-and-bounding-box span indexes — so “cite the page
this was read from” is a lookup rather than a mapping, and a mapping can disagree.
A chunk is never emitted for whitespace alone: a zero vector has no direction, and
not producing one costs no request and no row.

**And that ratio is an English assumption, which is a finding rather than a
footnote.** The same book chapter is 3,342 characters in English and 2,079 in
Japanese, yet Japanese runs near one token per character against English’s four — so
a 1,024-character Japanese chunk carries about four times the tokens the default
intends, and a chunk that overruns the model’s context is truncated *by the model*,
silently. The calibration that followed went against the hypothesis: over 384 to
2,048 characters at three overlaps, eighteen cells against a real embedder and this
project’s own documentation, recall moved 82–93% in English and 37–59% in Japanese
and **no cell was preferred**. Shrinking the chunk does not close the gap, so the gap
was never the chunk’s. What doubled Japanese recall was changing the *model* — same
questions, same corpus, 41% to 81%. The parameter was not the lever.

**A vector is a sealed binary column, one row per chunk, scanned in process.** No
extension, no second service, no approximate index — and every one of those was
measured before it was declined. SQLite’s vector extension cannot be reached from
this platform at all: the database binding exports no extension-loading entry point,
so `load_extension` answers “not authorized” while the identical library loads it
from the command line. PostgreSQL’s does work unmodified, and is still declined,
because a full scan is 8 ms at a thousand chunks, 74 ms at ten thousand and 759 ms at
a hundred thousand, against an index that takes 272 seconds to build. The threshold
to look again is written down — fifty thousand chunks for one team — and the window
cap is deliberately *the same number*, so a team whose window truncates has already
crossed the line where the whole approach is meant to be reconsidered.

**What made sealing affordable was discovering that the seal was a string API.**
Packed single-precision floats through it cost 51 times what the cipher costs and
1.8 times the storage, and none of that is encryption: it is base64 in, UTF-8 out,
UTF-8 in, base64 out, four whole-buffer conversions of which two inflate the value by
a third. Nothing had noticed, because the largest sealed value in the schema until
then was 200 KB of extracted text. At the bytes level the whole scan costs 4–14% more
than unsealed, so the privacy-first default is not the slow path — which is the only
reason a document vector can be sealed at all, and it must be, since embedding
inversion recovers much of a chunk’s source text.

**Authorization is per row, after the arithmetic, over four times as many candidates
as the caller asked for.** A document is many chunks, so the number of permission
checks is the number of distinct *documents* among the candidates, which a memo keyed
by object makes cheap. The headroom is the one approximation here and it is stated
rather than buried: if the ten nearest chunks all belong to a colleague’s private
document, the query answers nothing while a readable eleventh was a good match.
Authorizing the whole window first would close it exactly and costs one query per
document in the team, seconds at ten thousand documents, on a query path. So the hole
is pushed out four-fold rather than closed, and a scan that exhausts its headroom
*says so*.

A hit carries where to read and not the text: the store holds offsets and a vector
and no prose at all. Composing the passage is the retrieval tool’s job, and the tool
answers structure where the graph’s `kg_query` answers a sentence — both right for
their reader, because the whole point of carrying offsets is that a citation be
machine-readable, and flattening them into prose leaves a model retyping a key it was
handed.

**`?semantic=1` on search degrades; the retrieval tool refuses.** A caller asking for
a *search* gets the keyword half and a named reason the other did not run, because the
alternative leaves somebody asking for both worse off than somebody asking for
neither. A caller asking for exactly this gets the unset variable named and nothing
else. One asks for a service, the other asks for a capability. It is also the first
content search that survives the content-encryption switch: the keyword half is a SQL
`LIKE` and is dropped on a sealed instance, where the semantic half compares vectors
and unseals only the text it quotes.

## Asking the documentation

The same stack, pointed at the product’s own manual, is the `Docs` panel. Three
decisions in it are worth carrying away.

**The corpus belongs to the instance, not to a team**, because a document table row
needs a team: the shipped manual in a team would be ingested once per team, charge
each team’s storage, and be offered to each team’s knowledge-graph extraction.

**It is ingested by an operator command and not read off disk**, because the packaged
build does not contain `docs/` — a boot-time read works in every developer’s checkout
and finds an empty directory on every real install. An unchanged file costs no model
request, so a re-ingest after editing five pages costs five.

**“I don’t know” is two layers and neither is sufficient.** A similarity floor before
any model call, then every path the answer cites resolved against the passages that
were actually retrieved. The floor cannot be a relevance test, and the measurement is
why: a Japanese question that missed its chapter entirely still scored higher than an
English question that found the right file. And the one defect only a real model
found: asked something the documentation does not cover, the model refused correctly
*and then named all five passages by way of explaining what they were about* — so
five valid citations turned a refusal into a five-source answer. An answer that cites
every passage it was shown has cited nothing, and raising the floor is not the fix,
because the genuinely useful answer to a different question scored lower than that
refusal did.
