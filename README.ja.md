# Telemachus

[![CI](https://github.com/IoTone/Telemachus/actions/workflows/ci.yml/badge.svg)](https://github.com/IoTone/Telemachus/actions/workflows/ci.yml)
[![Nightly tour](https://github.com/IoTone/Telemachus/actions/workflows/nightly.yml/badge.svg)](https://github.com/IoTone/Telemachus/actions/workflows/nightly.yml)

[English](README.md) · **日本語**

**チーム向けに設計され、自分たちのインフラで動かす、プライバシーを第一に考えた AI
ツール／アプリケーションのためのプラットフォーム。** ローカル環境を前提とし、主に
`llama-cpp` / `llama-server` で駆動され、Python への依存は最小限。初日から
オープンである。

汎用のアプリケーション一式は **チャット**、**リサーチ**、**文書翻訳**。それを超えて
Telemachus は **SDK でありプラットフォーム** である：導入者はプラグインで機能を
拡張できる — 新しい **ツールと連携**、**データセット**、**ローカライゼーション** を、
安定した文書化された契約を通して。

最初のプロトタイプは **Racket** で書かれている。フロントエンドとバックエンドは
**差し替え可能** であることを意図している — 別のフロントエンド、別のバックエンドを
誰かが提供できる — したがって長く残る表面は **SDK の契約、バックエンドの API、
セキュリティモデル、そしてプロトコル** であり、個々の実装ではない。同じ契約に対する
もうひとつのリファレンス実装を、別のエンジニアが後から提供することを想定している。

## 系譜とライセンス

Telemachus は、以前の自ホスト型 AI ワークスペース（「Odysseus」）の後継であり、その
**概念** — データモデルの発想、ツール／エージェント契約の形、プロバイダーの抽象化、
ハードウェアを意識したローカルモデルの提供 — を再利用するが、**クリーンな MIT/X
ライセンスのプロジェクト** である。持ち込まれているのは著者自身が書いたコードと
ドキュメント（Racket の実装と著者が書いたドキュメント）のみであり、第三者のコードや
借用したソースは取り込んでいない。出自はファイル単位で確認している。

これは **純粋な OSS** である。オープンコアモデルは採らず、「オープンコアの
ちゃぶ台返し」を行う計画もない — 隠し持った商用階層はなく、機能の有料化もない。
すべての機能が同じ MIT/X の条件で出荷される。

## 設計の原則

1. **チームが第一、RBAC が中核。** チーム／グループという実体のある概念と
   **ロールベースのアクセス制御** — 管理者かどうかの二値フラグではない。ロールが
   機能、データ、管理操作を制御する。
2. **クォータと公平な利用。** ユーザーごと／チームごとの **クォータ** はチーム設計の
   一部であり、後付けではない。
3. **AI の同時実行を制御する — 事故による自己 DDOS をしない。** AI の利用と
   多段のアプリケーションフローは **キューに入り、レートと同時実行数を制限される** ので、
   暴走したエージェントやフローの集中が、意図せずホストや上流のモデルサーバーを
   DDOS したり使い切ったりすることはない。
4. **すべての機能が管理できる。** どの機能も **しっかりした管理インターフェース** と、
   **有効化／無効化** の明確な手段を備えて出荷される。
5. **ローカル第一、プライバシー第一。** オフラインでローカルモデルに対して動作し、
   ユーザーのデータは導入者のインフラに留まる。
6. **Python は最小限。** ほとんどは `llama-cpp` / `llama-server` から駆動される。
   ML／文書／ネイティブの領域（埋め込み、拡散モデル、PDF、音声認識・合成）は —
   そもそも必要な場合に限り — 安定した JSON 契約を持つ小さなサービスの背後に
   隔離され、中核に織り込まれることはない。
7. **フロントエンドとバックエンドは差し替え可能、契約が鍵。** SDK の契約、
   バックエンドの API、セキュリティモデル、プロトコルが製品であり、実装は
   置き換えられる。
8. **ドキュメントが中心。** オープンなプロジェクトとして、ドキュメントはコードと
   並ぶ一級の成果物である。

## データ層

プロトタイピングは **SQLite** から始め、規模とチームの事情が求めるところに応じて
**PostgreSQL へ移行** できるように永続化層を設計する。データモデルは SQLite 固有の
挙動を前提にしてはならない。

## リポジトリの構成

設計ドキュメントはリポジトリの **ルート** に置き、各バックエンド／リファレンス実装は
`refimpl/<name>/` の下に置く。

- `README.md`、`ACKNOWLEDGMENTS.md`、`docs/` — プロジェクトの設計ドキュメントと帰属表示。
- `docs/FeatureRequirements.md` — 要件（前身システムのレビューから起草）。
- **`docs/integrators-guide.md` — 自分たちの製品を Telemachus に載せる**：コンソールの
  テーマ設定、ツールの出荷、自前の画面と API の提供、バックグラウンド処理の追加。
  実例は `refimpl/racketmaximus/plugins/integrator-demo/`。
- `docs/reference/` — ソースから生成（ルート、ツール、ワークフロー、権限、プラグイン、
  SDK）してコミットしてある。差分が出れば CI が落ちる。日本語版は
  `docs/reference/ja/`。
- `docs/ops/` — 運用担当者向けの手順書（ワークフローエンジン、マルチテナンシー、
  文書リポジトリ、保存時の秘密情報）。
- `refimpl/racketmaximus/` — 最初のリファレンス実装（Racket）。独自の README を持つ。

追加のリファレンス実装（別のバックエンド、あるいは別のエンジニアの設計）は、同じ契約に
対する兄弟ディレクトリ `refimpl/<name>/` として差し込まれる — プラットフォームの
どの部分も、特定の実装に結びついてはいない。
